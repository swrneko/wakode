# wakode 3a — фундамент сервера

Дата: 2026-08-17. Предшественники: `2026-08-15-wakode-design.md` (общий дизайн), планы 1 (`wakode-core`) и 2 (`wakode-store`) — оба реализованы и слиты в `master`.

## 1. Границы

Серверная часть волны 0 разбита на два плана. Этот — **3a, фундамент**: конфиг, криптография, аутентификация, CLI, каркас axum. Следующий — 3b: шесть совместимых эндпоинтов и внутренний API.

Шов проходит там, где кончается инфраструктура и начинается предметная область. **В 3a нет ни одного прикладного эндпоинта.** Конец 3a: сервер поднимается, применяет миграции, принимает API-ключ и сессию, отвергает неверные с различимыми причинами, CLI создаёт пользователя и выдаёт ключ, бэкап работает. Полезной работы сервер при этом не делает никакой.

Разбиение выбрано потому, что 3a и 3b — работа разного рода. Форма ответов 3b заморожена чужим протоколом и проверяется golden-фикстурами с живого wakatime.com; 3a не зависит от внешних источников вовсе и проверяется целиком на месте.

## 2. Крейты

Готовы и слиты: `wakode-core`, `wakode-store`. В 3a создаются три: `wakode-auth`, `wakode-api`, `wakode`. Шестой крейт исходной спеки, `wakode-web` (статика SPA), появляется в плане 4.

### `wakode-auth` (новый)

Вся криптография проекта. Чистые функции над байтами: ни БД, ни HTTP, ни файловой системы, ни времени.

- argon2id — хеширование и проверка паролей;
- симметричное шифрование значения API-ключа мастер-ключом: AEAD со случайным nonce на каждое значение, предполагается XChaCha20-Poly1305 (широкий nonce снимает вопрос о коллизиях при случайной генерации). Точный крейт и версия фиксируются при написании плана, после сверки с актуальной документацией;
- HMAC-SHA256 — детерминированный отпечаток ключа для поиска (`key_lookup`);
- генерация значения API-ключа — **UUIDv4**, потому что плагины валидируют ключ как UUID с проверкой версии `[1-5]`, и UUIDv7 такую проверку не пройдёт;
- генерация и хеширование токена сессии.

**Зачем отдельный крейт.** План 2 двенадцать задач подряд держал правило «в хранилище нет криптографии»: `password_hash`, `key_encrypted`, `key_lookup`, `token_hash` там — непрозрачные байты. Правило удалось выдержать ровно потому, что криптографии было обещано место снаружи. Размазанная по обработчикам axum, она перестала бы быть проверяемой границей: убедиться, что секрет не утёк в лог или в ответ, стало бы можно только чтением всех обработчиков. Отдельный крейт делает проверку механической — как `wakode-core` доказывает изоляцию от I/O списком зависимостей, так `wakode-auth` доказывает, что криптография в одном месте.

Побочная выгода: крейт покрывается тестами в памяти, без БД и без сокета.

### `wakode-api` (новый)

Каркас axum: состояние приложения, извлечение и проверка учётных данных, преобразование ошибок в ответы, перехват паники. Подмодули `compat` и `internal` заводятся пустыми — наполняет их 3b.

### `wakode` (новый, бинарь)

Разбор конфига, применение миграций на старте, запуск сервера, подкоманды CLI.

## 3. Учётные данные

Два вида, оба разбираются в `wakode-api`.

**API-ключ.** `Authorization: Basic base64(ключ)` либо `?api_key=`. Префикс `waka_` срезается перед поиском. Отпечаток считается HMAC'ом, ключ ищется одним запросом по `key_lookup` — по зашифрованному значению искать нельзя, ради этого отпечаток и лежит отдельной колонкой с уникальным индексом.

Отозванный ключ **находится**, но даёт `401` с причиной, отличной от «ключа не существует». Хранилище умеет их различать (`revoked_at`), и это различие не должно потеряться на пути наружу.

**Сессия.** Непрозрачный случайный токен в cookie `HttpOnly`, `Secure`, `SameSite=Lax`. В базе — только хеш токена. Проверка истечения по `expires_at` делается здесь: хранилище отдаёт значение как есть, доменной валидации в нём нет по построению.

## 4. Конфигурация

Один файл, путь из `--config`, по умолчанию `./wakode.toml`. Сверху перекрывают переменные `WAKODE_*`. Каскада поиска нет намеренно: один путь — один ответ на вопрос «какой файл он прочёл». Абсолютные пути конфига и базы печатаются в лог при старте.

```toml
[server]
listen = "127.0.0.1:9000"
public_url = "http://localhost:9000"

[database]
path = "./wakode.db"
write_queue = 256

[auth]
registration = false
session_ttl_days = 30
setup_from_any_address = false   # см. §6, окно первичной настройки

[durations]
timeout_secs = 900
tail_padding_secs = 0
```

`listen` по умолчанию петлевой: инстанс, выставленный наружу, должен быть выставлен осознанно.

`tail_padding_secs = 0` — открытый вопрос исходной спеки: добавка последней отметке сессии не задокументирована WakaTime и калибруется по живому аккаунту. До калибровки wakode недосчитывает хвост каждой сессии. Не блокирует работу, блокирует совпадение цифр.

Мастер-ключ в файле не хранится — только `WAKODE_MASTER_KEY`, 32 байта в base64. Разделение носителей и есть весь смысл шифрования: файл с ключом рядом с базой означает, что украденный бэкап содержит и шифротекст, и ключ к нему.

## 5. Последовательность старта

Она же — порядок отказов. Каждый шаг падает со своей причиной.

1. Прочитать конфиг. Файла нет — сказать, какой путь искали, абсолютным.
2. Прочитать `WAKODE_MASTER_KEY`. Не задан — запомнить и идти дальше: инстанс без выданных ключей стартовать имеет право.
3. Открыть базу, применить миграции. Схема новее сборки — отказ с версиями обеих сторон.
4. **Мастер-ключ не задан, а в базе есть хоть один API-ключ — отказ стартовать.** Иначе сервер поднялся бы и молча отвечал `401` на все ключи, а владелец искал бы поломку в хранилище.
5. **Мастер-ключ задан и ключи есть — проверить, что он тот самый**: расшифровать один. Не сходится — отказ. Подменённый ключ иначе даёт ту же тихую поломку, только позже и незаметнее.
6. Поднять пишущую задачу и сервер. В лог — пути, адрес прослушивания, число применённых миграций.

Шаги 4 и 5 — не перестраховка, а единственная защита от отказа, который выглядит как поломка совсем другой части системы.

## 6. Первичная настройка

Первый пользователь создаётся через экран первичной настройки (как в Gitea и Grafana), а не только через CLI: `registration = false` в конфиге на этот экран не влияет.

**Окно гонки.** Пока в базе нет ни одного пользователя, эндпоинт настройки открыт — в это окно чужой может занять инстанс. Закрывается так: настройка принимается **только с петлевого адреса**, если в конфиге явно не разрешено иначе (`setup_from_any_address = true`). Проверка нужна отдельно от `listen`: за обратным прокси адрес прослушивания петлевой, а адрес клиента — нет.

Владельцу, ставящему сервер сразу за прокси, придётся один раз разрешить это явно либо создать пользователя через CLI. Дефолт закрыт.

Сам HTML-экран — план 4; в 3a это эндпоинт и его правила доступа.

## 7. CLI

Все подкоманды читают тот же конфиг, что и сервер, через общий флаг `--config`. Иначе `wakode user create` пошёл бы не в ту базу.

```
wakode serve                              # подразумевается, если подкоманда не указана
wakode migrate
wakode master-key generate
wakode user create --login … [--admin]
wakode user list
wakode key issue --user … --name …
wakode key revoke --id …
wakode backup --to …
```

Пароль флагом не принимается: он остался бы в истории оболочки и в выводе `ps`. Спрашивается интерактивно.

Значение API-ключа печатается один раз при выдаче. Расшифровать его потом можно — за этим и хранится шифротекст, — но делать это через CLI незачем: для показа есть настройки в интерфейсе.

## 8. Проверка

**`wakode-auth`** — в памяти, как `core`:
- круговой обход шифрования значения ключа;
- отпечаток одного ключа стабилен между запусками, у разных ключей различен;
- argon2 принимает свой хеш и отвергает чужой;
- **значение, зашифрованное под одним мастер-ключом, не расшифровывается другим** — тест, ради которого существует шаг 5 старта;
- `Debug` ни одного типа не печатает секрета. Урок финального ревью плана 2: производный `Debug` дампил весь словарь строк и `password_hash` дословно, и увидеть это удалось только на стыке трёх решений, каждое из которых по отдельности было разумным.

**`wakode-api`** — через `tower::ServiceExt::oneshot`, без поднятия сокета:
- верный ключ → `200`; отозванный → `401`, причина отличается от «не найден»; несуществующий → `401`;
- истёкшая сессия → `401`;
- префикс `waka_` срезается;
- ключ из query-параметра работает наравне с заголовком;
- паника в обработчике → `500`, процесс жив;
- настройка с нелокального адреса при закрытом дефолте отвергается.

**Последовательность старта** — отдельными тестами на временной базе: каждый шаг роняется по очереди, проверяется, что сообщение называет причину. Шаги 4 и 5 обязательны.

**`wakode`** — CLI прогоняется как процесс на временном конфиге: `migrate`, `user create`, `key issue`, `backup`. Отдельно: `key issue` печатает значение; `user create` не принимает пароль флагом.

## 9. Долги, которые 3a обязан закрыть

Унаследованы от планов 1 и 2, записаны в их журналах:

1. **`Debug` у `IncomingHeartbeat`** производный и печатает путь к файлу, а `WriteJob` в пишущей задаче несёт целый батч — один `?job` в логе выведет все пути. При добавлении `tracing` это надо решить осознанно: для входного DTO путь в отладочном логе обычно и нужен, но решение должно быть записано, а не унаследовано по умолчанию.
2. **Шов для управляемого завершения писателя.** `StoreError::WriterGone` не покрыт ни одним тестом, и молчаливая смерть потока писателя при панике ничем не сигнализируется. Обе парковки плана 2 закрываются одним швом — здесь.

## 10. Долги, передаваемые в 3b

Из ревью плана 1, сюда не относятся, но потеряться не должны:

- `"unknown"` → `null` перед отдачей совместимому клиенту;
- `Micros` на проводе — дробные секунды, а не целое;
- `dependencies` — список, а не строка через запятую, и в `Copy`-структуру `Attrs` он не помещается;
- `summaries` обязан отдавать пустые дни, которых разбиение по локальным дням не возвращает;
- точная форма `statusbar/today` — снимается с живого ответа, документации нет.

## 11. Открытые вопросы

1. **`tail_padding`** — величина неизвестна, калибруется по живому аккаунту WakaTime. Не блокирует 3a (параметр уже вынесен в конфиг), блокирует совпадение цифр с WakaTime.
2. **Golden-фикстуры для 3b** снимаются с живого аккаунта. Внешняя зависимость: без них совместимость непроверяема, и начинать 3b до их появления бессмысленно.
